# smtv

The `smtv` command and the window: tools found through entry points, `smtv doctor`, models and keys, the page
(`smtv serve`), the window (`smtv app`), updates and plugins, Docker. Rules of the whole repository: the root
`AGENTS.md`; the core it builds on: `packages/smtv-core/AGENTS.md`. Tests: `packages/smtv/tests`.

## The page (`smtv serve`)

- `packages/smtv/src/smtv/serve.py` (HTTP, standard library only) and `jobs.py` (job processes); static files in `smtv/web/`, no build step.
- Safety, each rule with a test in `packages/smtv/tests/test_serve.py`:
  - listens on 127.0.0.1 only; any `Host` other than `127.0.0.1:<port>` or `localhost:<port>` gets 403, GET and SSE included (DNS rebinding);
  - every change (start, cancel, run again, key, settings, switches, upload) needs the session token in `X-SMTV-Token`: random, made at server start, written only into `index.html`; without it, 403. GET requests change nothing;
  - on changes, a foreign `Origin` or a `Sec-Fetch-Site` other than same-origin gets 403;
  - no CORS headers, ever;
  - keys go in, never out: answers say only whether a key is saved and whether it works; never in answers, error texts, events or logs (`smtv_core.llm.keycheck.redact`).
- A tool plugs into the window by setting `Tool.page` (`smtv_core.tool.Page`); `start` turns its form into `smtv <tool> <args>`, which the page runs in its own process (one running job per tool) and cancels by stopping that process group.

## The window's layout and a tool's places in it (stage 7)

- Nothing moves on hover or focus: hover only changes colour or shows what already has its place (fixed row heights, fixed widths for parts that appear).
- The look is calm and plain, like Claude and ChatGPT: neutral greys, no gradients, glows or display type; colour only for a job's state. Strict minimalism: nothing in the frame that the content does not need.
- The frame is the gateway's (`smtv/web/`): a top bar with what runs now and, while a request is open, its name after a short divider (`api.setTitle`; on macOS also the window's buttons; the whole bar moves the window), a narrow rail of icons on the left — Home, Scheduled (a clock), Plugins (a plug), the tools' own items; at the bottom Connect a phone (stage 9) and the profile (a small menu opening upwards, like Claude's: the StreamMoment account's name or this computer, «Sign in» or «Account», Settings, and «Log out» of the account only when signed in — quitting SMTV is in Settings → System; tokens are still counted — `GET /api/usage`, the `usage` part of the window's stream — but not shown for now; language and theme are in Settings → Language and theme, «Support the project» at the bottom of the Settings list). Icons only, no captions or «soon» marks; light grey, a rounded square on hover, the open one white and filled on that square. While another window is in front (`document.hasFocus()`), the rail, the section's side list and the top bar turn grey; the content does not change. The top bar and rail sit on the window with no lines between them; the work area is one panel with a rounded corner. Every word of the window is in `web/i18n/<language>.json` (`en.json` the source, `ru.json`, more through Weblate: `docs/translations.md`); the language is the system's until one is chosen in Settings → Language and theme, and a key a language lacks is shown in English. The Python side (dialogs, notifications, refused pages, «Coming») reads the same files through `smtv.i18n`. On a phone-width window the rail becomes a bar at the bottom.
- Every page is built with one component (`screen` in `app.js`) in one of two formats: with a side list (Home: the requests; Settings: its sections — the list on the left, the open item on the right, one at a time on a narrow window) or the content alone (Plugins, a plugin's page, Scheduled, Phone, a tool's rail item). A new page picks one of the two; no third layout. The side list is 232 px wide; its right edge is a thin line the person drags (180–420 px, the resize cursor and a lighter line on hover, a double click resets it), kept between starts; the top bar's request name follows that edge.
- Settings is a page (`#/settings/<section>`): Account (StreamMoment), Providers, Agents, Speech, a section per tool with switches or `mountSettings`, Language and theme, System (checks, quit, remove), About.
- Home lists every tool's jobs as one list of requests, newest first (`GET /api/jobs`), like chats: «New request» is the first row (as «New chat»), then each request as one row — the channel's round picture (or the tool's icon for a file), the title, and a dot: white — something new (running, or changed since it was last opened; remembered in the window), red — failed, yellow — paused; none when done and seen. A request dragged up into «Pinned» stays above the day groups (the area shows while dragging and lights up under the pointer); dragged back down, it is unpinned. The drag is the page's own (pointer events, a copy of the row follows the pointer): the browser's drag and drop never delivered the drop inside SMTV's window. «Pinned» has the person's own order: while a row is dragged over it, an empty row-high slot opens where it would land; dropping there pins it at that place, dragging a pinned row moves it; the pin button puts a request on top. Pins and their order are kept in the window's storage. Every group (Pinned, Today, …) folds by a click on its name. On hover a row shows «pin/unpin» and «delete» instead of its dot. Deleting removes the whole job folder for good: the page asks in its own modal dialog (the focus on «Cancel»), then `POST /api/jobs/<tool>/<job>/delete` with the token and `{"confirm": "delete"}`; refused while the job runs (409) and for anything outside the tool's jobs folder. «New request» offers each tool's kind of request; an open request is the tool's own view.
- «New request»: a question and one field in the middle of the page (VodCut: a link or a path, a file button, «Start»; one quiet line with the estimate), no other settings; while it is open a file dropped anywhere in the window is uploaded and started at once. Elsewhere a dropped file is ignored (the window never opens it). The speech language chooses itself (`smtv_core.asr.language.choose`): the recording's own language when it says one (YouTube), otherwise Russian unless Parakeet is on this computer, then detected.
- VodCut's open request: its state as a quiet word with a small dot, not a badge; each clip only as its picture with a round blurred «play»; a press opens the viewer: a large modal, the clip playing on the left; on the right its title, description and keywords (each with «copy»; VodCut does not write the last two yet), «Download», and the clip's transcript from the job's `transcript.json` moved into the clip's time, the word being said lit as it is said (the clip and its burned captions are never touched); the clips straight on the window's background, the recap first and three clips wide (its cover as the poster, «play» opens its own wide viewer with the chapters, the description, «Download» and «Cover»; while it is made, its step; switched off, a word and «Turn on in Settings»); on the right a column of floating widgets (the request with its channel and controls, progress with the stages folded, numbers, then episodes, live feed and model calls folded), each folded or open as last left. Clip columns get exact widths, not `1fr` (WebKit squeezed fr tracks next to the spanning recap).
- A job's picture is the tool's `describe(folder)["avatar"]`, a file in the job folder. VodCut takes it from the channel's public page (`og:image`, Twitch and YouTube image hosts only; `vodcut/avatar.py`), once per channel, in the background, not again for a day after a failure; never through private APIs or keys.
- A tool's places, each optional, declared in `Page` and drawn by its `section.js` (no change to the gateway): `request` (a `RequestKind` under «New request», drawn by `mountNew(el, api)`), `mountJob(el, api, job)` (an open request; returns `{close}`), `nav` (a `NavItem` in the rail, drawn by `mountNav(el, api, path)`), its block in Settings (`options` switches and/or `mountSettings(el, api)`), its checks under System (`Tool.checks`, grouped by tool: `doctor_groups`), its card and page under Plugins (`summary`, `about`, `icon`). The tool's own words are files beside its `section.js`, `i18n/<language>.json` (`en.json` the source): `api.t` looks there first, then in the window's; a tool's key never changes the window's text or another tool's. Text the window shows can be one string or one per language.
- Not installed: no trace anywhere. Fails to load (entry point) or its `section.js` fails: listed under Plugins as broken, its jobs still listed; nothing else depends on it. A tool whose job folder cannot be read is skipped in the list, never the others.
- Plugins lists installed, broken, available (`CATALOG`) and announced (`SOON`, never installable) tools, with SMTV's own version and updates on top. «Install» and «Remove» on a plugin's page go through the updater (below); an SMTV installed from source (editable) or without uv or pip shows the command instead.
- The page shows a job only from its journal: SSE at `/api/jobs/<tool>/<job>/events`, `id:` = event number, a reconnect sends `Last-Event-ID` (or `?after=N`) and gets the rest with no gap and no repeat.

## The window's state: one stream, one store (stage 8)

- The window never polls. `GET /api/window/events` (`hub.py`) is one SSE stream for the whole window: `snapshot` first (requests, what runs now, tokens, updates), then `job` (a request appeared or changed), `job_gone`, `activity`, `usage`, `update`. One thread looks at everything about once a second, only while a window listens, and starts each new stream from a fresh look; every change through the API pokes it. A reconnect gets a new snapshot, so nothing is lost. An open stream counts as an open page.
- The page keeps that state in signals (`live.jobs`, `live.activity`, `live.update`… in `app.js`, also `api.live` for tools; `signal`, `computed`, `effect`, `batch` from `web/dom.js`, no Proxy, no dependency): a view is an effect that reads the signals it shows and runs again when one of them changes (`liveBox` follows one part and lets go once it left the page). A tool's page does the same with its own signals (VodCut: one signal per part of a request, an effect per part and per clip card). No framework, no build step. One way the page changes (V6): state → subscriptions → only the nodes that changed. `web/dom.js` (also on `api` for tools) has `text` and `attr` (written only when different), `keyed` (a list follows its items by key: new nodes added, gone ones removed, changed ones updated in place, order fixed by moving), `blocks` (a page of blocks, each rebuilt only when its sig changes) and `region`. Nothing is rebuilt to show the same thing again, so focus, hover, selected text, open details, videos and scroll stay by themselves; the clock of a running request touches only its own text. Tests: `node --test` over `packages/*/tests/web/*.test.mjs` on a small fake DOM that records every change (`python scripts/check.py web`). A request's own events stay on `/api/jobs/<tool>/<job>/events` (two connections per window at most).
- Job info is cached by the journal's size and time, the process and the pause request: the stream does not re-read unchanged journals every second.

## Updates and plugins from the window (stage 8)

- `updates.py`: once a day (a while after the start, then whenever 24 h have passed; `Settings.tools["smtv"]["update_check"] = false` turns it off — Settings → System) and by «Check now», SMTV reads the update channel (stage 27, `channel.py`): `latest.json` beside the latest GitHub release, believed only with a valid Ed25519 signature by the key in `channel.PUBLIC_KEY` (the private key is the release workflow's secret `SMTV_UPDATE_SIGNING_KEY`; `scripts/release_manifest.py` makes and signs the manifest). It names the version, its changes (from `CHANGELOG.md`) and each kind of install's files with sizes and SHA-256 sums. A manifest older than the newest one accepted before (`run/updates.json`) is refused. The window shows «Version X is available» and the changes, plain text, only versions newer than the installed one. uv and pip installs download the wheels of the manifest into `run/update-files/<version>`, check them and install from those files; the desktop apps (`dmg`, `exe`, marked by `smtv-install-kind` beside their Python) download and open their installer; Docker is told and shown the command.
- An update, an install or a removal: SMTV writes a plan (`<SMTV home>/run/update-plan.json`: commands, the versions before, how to start again), copies `updater.py` to `<SMTV home>/run/`, starts it detached with the Python the environment was made from (outside the environment: the installer replaces it, and Windows locks the files of a running program) and quits a second later; the window says «Updating SMTV». The updater waits for the old process to end, runs `uv tool install --reinstall "smtv[<tools>] @ file://…/smtv-X-….whl" --with "smtv-core @ file://…" …` for an update (`smtv[<tools>]==X` from the index for a plugin install or a rollback) (pip: `pip install --upgrade …`, plus `pip uninstall -y <tool>` for a removal), starts SMTV again the way it was started (`open SMTV.app` when it ran from SMTV.app, else the same command and options) and waits for `/api/hello` to answer with the expected version and tools. Otherwise — a failed step, an early exit, no answer in 180 s — it puts back the versions written down before and starts SMTV again; if even that fails, a system dialog points to `<SMTV home>/logs/update.log`. The result (`run/update-status.json`: done, rolled_back, failed) is shown once by the next window and stays on the update card. `updater.py` uses the standard library only (a test checks it).
- While jobs run, an update waits for them (the updates thread starts it as soon as none runs, with or without a window), or «Stop the jobs and update» stops them first; «Continue» resumes them afterwards from the same step.
- Safety: only `smtv`, `smtv-core` and `CATALOG` tools are installed or removed, by names in this code; a name from the page is only looked up in that list (`not_in_catalog` otherwise; `SOON` tools too). Versions from the manifest are used only when it is signed and they are plain release numbers (`updates.parse`); files only when their size and SHA-256 match. Commands are argument lists. The index is `https://pypi.org`; `SMTV_INDEX` (the person's own environment, never the network) may point to another index for tests and mirrors: https, or http on this computer only; it goes first, PyPI stays for dependencies. Every action needs the session token and our own origin, like any change.
- Tests: `packages/smtv/tests/test_channel.py` (signatures, a swapped file, no network, an old manifest, each kind of install, the release script) and `packages/smtv/tests/test_updates.py` (fake channel; the updater as a real process with fake installer and fake SMTV: update, rollback on a failed install, on a version that does not start, on a plugin missing after install; waiting for jobs; names outside the catalog). Live check on a Mac: a local index of built wheels and a `uv tool` install in a test folder (the plan in the StreamMoment repository records it).

## SMTV as a program (`smtv app`, `smtv shortcut`)

- `smtv app` (`desktop.py`) is what the SMTV icon runs: one process, the server and SMTV's own window (`window.py`, pywebview: WebKit on macOS, WebView2 on Windows, GTK or Qt on Linux). The process lives as long as its window; nothing runs in the background on its own. No tray, no autostart, no browser install. Output goes to `<SMTV home>/logs/app.log`.
- The window is built hidden and shown when the page has loaded (its first frame is already right). The server marks the page for it (`?window=mac|win|linux` → `<html class="shell shell-mac">`), so the header never shifts. On macOS: no title bar (`FullSizeContentView`, transparent title bar; pywebview paints the title bar grey, so it is made clear; WebKit's automatic top inset is off), the native buttons in the middle of the page's top bar (`HEADER_PX`, again after each resize and each change of appearance), the top bar and the rail's empty space drag the window (`webkit.messageHandlers.smtvWindow.postMessage('drag')` → `performWindowDragWithEvent_`, a double press zooms), corners 24 pt through the private `_setCornerRadius:` when the system has it.
- Glass on macOS: the window is not opaque, WebKit draws no background, and an `NSVisualEffectView` (UnderWindowBackground, behind the window, state always Active — following the window's active state blinked on redraws) sits inside the WebKit view below the page. A user script gives the page the class `glass` from the first frame only when that worked; then the top bar, rail and list of requests are see-through and cards stay dense. The page sends `theme:dark|light|auto`; the window takes that appearance (auto: none of its own, so it follows the system, and so does the page's `prefers-color-scheme`). The light rim the system draws around every window comes with its shadow and is left alone; a slightly lighter inner edge on the page makes it stand out less.
- Windows keeps its own frame (a frameless pywebview window there cannot be resized from its edges or snapped); its title bar takes the page's colours (`DwmSetWindowAttribute`: dark mode, caption and text colour on Windows 11). Downloads are on (a save dialog); external links open in the browser.
- Closing the window: nothing running → the process quits. Jobs running → a native question: go on in the background (the window goes to the Dock or taskbar; a notification says when a job is done or failed; the Dock icon shows the job count), stop and quit, or cancel. «Quit SMTV» in Settings (`POST /api/quit`) closes it too.
- One SMTV at a time: a second start finds the running one (`/api/hello`) and asks it to bring its window forward (`POST /api/window/show` with the session token from `<SMTV home>/run/session.json`, mode 600, removed on exit). On macOS SMTV.app's script `exec`s Python, so the running process is SMTV.app's and macOS itself brings the window forward.
- No native window possible (Linux without GTK or Qt bindings): the page opens in the browser, and with no open page (an open window stream; the older `/api/activity?page=<id>` still counts, 90 s grace) and no running job for `IDLE_MINUTES` (5) SMTV stops by itself. `smtv doctor` says how to get the window.
- A taken port is a system dialog, never another port.
- `smtv shortcut [--remove]` (`launcher.py`), no administrator rights: `~/Applications/SMTV.app` (macOS, registered with `lsregister`), `SMTV.lnk` on the desktop and in the Start menu with `pythonw` (Windows), `smtv.desktop` in the menu and on the desktop (Linux). Tests check what is written (`System` takes the home folder and helper commands) without writing it.
- The process is named SMTV, not Python: the system names a process after the file it started from. macOS framework builds (python.org, Homebrew) get a copy of the inner `Python.app/Contents/MacOS/Python` (~50 KB) as `SMTV.app/Contents/MacOS/smtv-python` with `__PYVENV_LAUNCHER__`, so the Dock and Activity Monitor show SMTV.app's name and icon; the script tries the copy first and falls back to plain Python (the copy is tied to the installed Python version; `smtv shortcut` after an upgrade makes it again). Other Pythons (Linux, standalone builds) start through a symlink `SMTV` next to `pyvenv.cfg` (not in `bin/`, where `smtv` is: one name on macOS). Windows still shows pythonw.
- The first run of any `smtv` command by a person at a terminal (`cli.at_terminal()`; never jobs the page starts, scripts or tests) makes the icon once (`Settings.tools["smtv"]["shortcut"]`: `made`, `failed`, or `removed` after `smtv shortcut --remove`, which is respected). `SMTV_NO_SHORTCUT=1` turns it off; Linux without a display is skipped.
- Removing SMTV (`uninstall.py`): `smtv uninstall [--data]` or the window (Settings → System, `POST /api/uninstall` with the token and `{"confirm": "remove"}`), then SMTV quits. It removes the icon, then `uv tool uninstall smtv` a few seconds after the process quit (an install without `uv tool` is left alone and the command printed); clips, jobs, settings and keys only with `--data` / the checkbox, and only from a folder that is plainly SMTV's. The answer carries `Clear-Site-Data: "cache", "storage"` for anything an older SMTV left in a browser.
- `activity.py` folds the running jobs' journals into one summary (`/api/activity`): the page's header and window title, the Dock badge, notifications (`desktop.Watcher`, tested without windows).
- Notifications on macOS come from SMTV itself (UserNotifications, `pyobjc-framework-UserNotifications`), with SMTV's name and icon: macOS allows that only to a signed app, so `smtv shortcut` signs SMTV.app and its Python copy locally (`codesign --sign -`, ad-hoc: no certificate) with SMTV's identifier; the first start asks the person once. Not allowed or started from a terminal: osascript (Script Editor's icon). They speak the page's language (`/api/activity?lang=`), not the system's.

## Docker (stage 21)

- `Dockerfile` and `compose.yaml` at the root; the image sets `SMTV_DOCKER=1` and `smtv serve` reads its environment in `packages/smtv/src/smtv/container.py`.
- In Docker the page listens on every address inside the container and every request needs the access key (`/?token=` from the log → cookie `smtv_access`) on top of the page's rules above; `/healthz`, `/manifest.webmanifest` and the icons are the only routes without it. The Host must be one of the published names (`SMTV_PUBLIC_PORT`, `SMTV_HOSTS`, `SMTV_LAN_ADDRESS`). Tests: `packages/smtv/tests/test_docker.py`.
- Nothing goes into the image that a person does not need to run SMTV: no yt-dlp (links go through the StreamMoment account; VodCut does not depend on it), no Codex or Claude Code CLI, no keychain package.
